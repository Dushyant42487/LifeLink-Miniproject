### Why Registration Requests Were Not Persisting

Registration requests were indeed **failing to persist to Supabase**, caused by three issues:

1. **Schema Column Mismatches**:
   - The code added fields (`postalCode`, `latitude`, `longitude` on donors; `postalCode` on hospitals/blood banks) that do not exist in the Supabase table definitions.
   - Supabase PostgREST strictly rejects upserts that contain unmapped columns:
     ```
     PGRST204: Could not find the 'latitude' column of 'donors' in the schema cache
     ```

## Unified Multi-Project Gateway & Chatbot Integration Log

### Architectural Decisions & Overview:
1. **Decision**: Built a lightweight reverse-proxy API Gateway ([gateway.js](file:///c:/Users/harsh/OneDrive/Desktop/LifeLink-Miniproject/gateway.js)) using `express` and `http-proxy-middleware` to blend the LifeLink Main Platform (React/Vite :5173 + Express API :5001 + FastAPI ML :8000) and the LifeLink Chatbot ("chatboot" :3000) into a single cohesive origin (`http://localhost:8080`).
2. **Decision**: Zero code modification principle — preserved internal logic of both projects completely untouched, using gateway-level routing, URL rewrites, and WebSocket upgrades.

### Problems Faced & Solutions Implemented:

#### Problem 1: Chatbot Static Assets Breaking Under Sub-path `/chat`
- **Issue**: In `chatboot/public/index.html`, stylesheet and scripts are referenced with relative URLs (`style.css`, `app.js`). When a user visited `http://localhost:8080/chat` (without a trailing slash), the browser treated `/chat` as a leaf resource, resolving relative assets to `http://localhost:8080/style.css` and `http://localhost:8080/app.js`. These requests fell through to the Vite frontend proxy and returned 404 / HTML responses.
- **Solution**: Added an explicit 301 trailing-slash normalization redirect in `gateway.js`:
  ```javascript
  app.get('/chat', (req, res) => {
    const query = req.url.includes('?') ? req.url.substring(req.url.indexOf('?')) : '';
    res.redirect(301, `/chat/${query}`);
  });
  ```
  Now, requests to `/chat` immediately normalize to `/chat/`, causing the browser to resolve assets to `/chat/style.css` and `/chat/app.js`.

#### Problem 2: Chatbot Hardcoded Origin-Root `/api/*` Endpoints Clashing with Main Backend
- **Issue**: In `chatboot/public/app.js`, six distinct endpoints used absolute origin paths:
  - Line 99: `fetch('/api/status')`
  - Line 129: `fetch('/api/documents')`
  - Line 223: `fetch('/api/upload-pdf')`
  - Line 296: `fetch('/api/camps?...')`
  - Line 705: `fetch('/api/blood-availability?...')`
  - Line 1242: `fetch('/api/chat/stream')`
  If the gateway blindly forwarded `/api` to the main backend (port 5001), the main backend would return 404 for all chatbot calls.
- **Solution**: Implemented an upstream routing filter `CHATBOT_API_ROUTES` in `gateway.js` mounted before the main backend `/api` proxy:
  ```javascript
  const CHATBOT_API_ROUTES = [
    '/api/chat', '/api/camps', '/api/districts', '/api/blood-groups',
    '/api/blood-availability', '/api/upload-pdf', '/api/documents', '/api/status'
  ];
  app.use(CHATBOT_API_ROUTES, createProxyMiddleware({ target: CHATBOT_TARGET, changeOrigin: true, ... }));
  ```
  This bridges all 6 chatbot APIs seamlessly without altering a single line in either project's code.

#### Problem 3: Server-Sent Events (SSE) Buffering & Socket Timeouts on `/api/chat/stream`
- **Issue**: Standard proxy middleware buffers streaming chunks and drops long-lived HTTP sockets after default timeouts (30s-120s), truncating streaming responses from Ollama LLM (`llama3.2:3b`).
- **Solution**: In `gateway.js`, set `buffer: false`, `timeout: 0`, `proxyTimeout: 0`, and added custom `proxyReq`/`proxyRes` event hooks that inject `X-Accel-Buffering: no` and `Cache-Control: no-cache, no-transform`.

#### Problem 4: Vite Hot Module Replacement (HMR) WebSocket Drops
- **Issue**: Vite dev server relies on WebSocket connections (`/@vite/client`, `ws://`) for instantaneous code updates. Standard HTTP proxies do not pass WebSocket upgrade handshakes.
- **Solution**: Enabled `ws: true` on the Vite proxy and attached an explicit WebSocket upgrade handler to the underlying Node HTTP server:
  ```javascript
  server.on('upgrade', (req, socket, head) => {
    if (viteProxy.upgrade) viteProxy.upgrade(req, socket, head);
  });
  ```

#### Problem 5: Port Collision Guard with Atomic MCP Server
- **Issue**: In `chatboot/server.js:23`, Atomic MCP Client connects to `http://localhost:8080/mcp`. If Atomic runs on port 8080, launching the gateway on port 8080 triggers an `EADDRINUSE` error.
- **Solution**: Made `GATEWAY_PORT` fully dynamic via `process.env.GATEWAY_PORT || 8080` in `.env` and documented the fallback to port `8090` if Atomic MCP occupies `8080`.

#### Problem 6: Single-Command Multi-Service Orchestration
- **Issue**: Launching 5 separate services (Gateway, Vite, Express Backend, FastAPI ML, Chatbot) manually required 5 separate terminal tabs.
- **Solution**: Integrated `concurrently` into root `package.json` with color-coded, labeled outputs and graceful `-k` process termination:
  `npm run dev` -> boots all 5 services concurrently.

## Authentication Route Resolution — POST /auth/register 404 Fix

### Problem Identified:
- **Error**: `{"success":false,"error":"Resource not found: POST /auth/register","statusCode":404}` occurred during user registration.
- **Root Cause**:
  1. The LifeLink Express Backend mounts all auth endpoints under `/api/auth` (e.g. `router.post('/register')` inside `app.use('/api/auth', authRoutes)`).
  2. The frontend `apiFetch` service prepends `API_BASE_URL` (`/api`) to all request paths: calling `apiFetch('/auth/register')` dispatches `POST /api/auth/register`.
  3. When requests traveled through the gateway on port `8090`, `app.use('/api', createProxyMiddleware({ target: 'http://localhost:5001' }))` matched on `/api`.
  4. By default, Express middleware strips the mount path (`/api`) from `req.url` before passing it to the proxy handler in `http-proxy-middleware v3`. Consequently, the proxy forwarded `POST /auth/register` to the backend on port `5001`.
  5. The backend on port `5001` only handles `/api/auth/register`, so it returned `404 Not Found: Resource not found: POST /auth/register`.

### Solution Implemented:
- In `gateway.js`, updated the `/api` proxy middleware to preserve the `/api` path prefix using `pathRewrite`:
  ```javascript
  app.use(
    '/api',
    createProxyMiddleware({
      target: BACKEND_TARGET,
      changeOrigin: true,
      pathRewrite: (path) => `/api${path}`,
      onError: createErrorHandler('Backend API (/api)'),
      on: {
        error: createErrorHandler('Backend API (/api)')
      }
    })
  );
  ```
- Gracefully restarted the gateway and backend processes.
- **Verification**: Executed registration test directly through gateway on port `8090`:
  - `POST http://localhost:8090/api/auth/register` -> Returned HTTP `201 Created` with valid JWT token and donor profile payload.
  - `POST http://localhost:5173/api/auth/register` (Vite dev proxy) -> Verified working.
